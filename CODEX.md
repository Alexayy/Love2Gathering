## Features used in this project

The implementation used parallel subagents with bounded ownership, coordinated by a main integration agent. Parallel subagents are a documented Codex workflow; each performs its own work and reports results to the parent. Shared file edits need deliberate ownership to avoid conflicts. [Official subagent documentation](https://learn.chatgpt.com/docs/agent-configuration/subagents).

| Workstream | Delegated work | Integration boundary |
| --- | --- | --- |
| Engine | Inspect XMage, compile the required modules, implement the Java transport and native prompt projection, exercise real rules and AI | JSON state/prompt contract and engine fixtures |
| Catalog and builder | Stream the JSONL into SQLite, implement search/storage/construction validation, extend builder controls and model contracts | Catalog endpoints, persisted deck shape and shared builder layout |
| Decks and assets/input | Prepare/validate the twenty lists, run engine load/game checks, inspect supplied font/image/audio metadata, curate assets and repair Slab editing | Validated deck files, asset API, text-input tests and provenance |
| Main agent | Coordinate requirements, review contracts, integrate the table, scaling, modals/settings and artwork, run the actual desktop client and inspect screenshots | Final application behavior and acceptance |

The work used shell commands for focused source discovery, builds and local runs; patches for reviewable edits; primary documentation and the supplied rules PDF for targeted checks; local image/asset inspection; real HTTP/service tests; deterministic engine fixtures; and actual LÖVE rendering with screenshots. The frontend uses LÖVE, Slab, a local Python service and XMage. Codex is a development tool, and the running client requires no OpenAI API key or OpenAI runtime API.

## Viewport, priority, theme and gallery follow-up

The table now opens on the human field at 1× world scale, rather than fitting every seat into miniature fields. Battlefield cards keep their world size, the header occupies about 104 logical pixels, and the terrain continues beneath a compact hand. Hover expands the hand and enlarges its focused card. Right-drag pans, the wheel zooms, and the overview is explicit. World/screen animation poses, card hits and scissors use separate but consistent coordinate spaces.

`PriorityController` asks XMage for meaningful native playable abilities and special actions, excludes native mana abilities alone, and uses native passing on the GAME thread. End Turn yields ordinary priority until a changed stack/turn, selected stop or required choice cancels it; normal empty-window automation then continues. The native playable calculation can conservatively retain a targetless action, so this is not a promise to suppress every possible extra question. An explicit stop or full control can retain empty priority for a bluff. UI stops use separate own/opponent indicators and an acknowledged gold status. The frontend blocks consumed prompt IDs during a pending command or when the native state says no priority is available; native snapshots must pair their prompt with the same current pending decision.

The Slab skin is an optional draw-command hook, preserving existing layout/input/clipping. Seven curated original PNGs use both provided Kenney packs, with original licenses and source paths. Full user-provided distributions remain untouched. `Theme.install` is applied from `View.new`, so all application views use the same skin. The fantasy divider is used beneath non-match navigation.

Gallery has per-printing and per-image-face credits, release year and variant filters. Only reviewed artist links are shown; unknown artists remain unlinked. That extension introduced API version 4 and `catalogSource` to prevent incompatible catalog reuse; the current launcher requires API 6. Missing metadata is explicit. Downloading full bulk metadata is opt-in and uses a new destination, preserving originals. Full-card/art-crop folders are exported mirrors of authoritative SQLite images; a larger cached full-card scan can satisfy a normal-size request offline without a duplicate SQL cache record.

Validation is separated by scope: 40 service/downloader tests; 15 frontend model, 16 priority model, 10 gallery model, 8 replay model and 90 camera checks; 267 actual multiplayer presentation checks including hover/pan/zoom, the user's requested 2537×1041 mode (actual desktop-clamped dimensions are recorded), and real saved projections; 16 theme and 19 font graphical checks; seven existing duel layout cases; and actual Gallery UI checks with four genuine Scryfall printings and JPEG artwork. `tests/gallery-ui-report.json` records the ready and missing-source gallery cases. ## Private rooms and native drafting

`service/rooms.py` now coordinates invitation-only human multiplayer and drafting. Every desktop owns a local HTTP proxy; the invitation includes the advertised room origin and a random join secret, while independent seat credentials remain within that proxy. Public rooms have no listing endpoint. `run.sh` starts the gateway alongside its owned engine; `scripts/run-room-server.sh` starts a public host without LÖVE and disables desktop-only `/client/*` routes, including requests through a loopback reverse proxy. Internet clients require a reachable configured host; no relay, NAT traversal service or external deployment is implied.

`MultiplayerBridge` maintains independent native games/drafts without replacing the legacy practice session. Each actual human has a separate `Session` perspective, prompt, priority policy and permitted information. `RoomSeat` maps stable external seat IDs across drafts and paired games. Host-perspective recording stays in the hosting catalog; guests cannot retrieve that recording or export another human's private hand. Native concession now uses the engine's asynchronous conceding-player queue and wakes blocked human input on the GAME thread, including an inactive player's concession.

`DraftSession` wraps native BoosterDraft/RandomBoosterDraft/DraftCube, native human and AI drafting, offered basics, Limited deck validation and Swiss/single-elimination tournaments. The installed profiles report 4–16 seats and three packs; native Commander rooms support up to ten players, while constructed duels support two. Traditional packs accept independent set selections. Cube choices are discovered from installed native classes. The native boundary also supports custom cubes, while the desktop selects bundled cubes. All paired games use stored pool-validated deck sources; supplied replacement lists and unbound winner claims cannot change outcomes. These are single-game pairings with Limited deck rules, not best-of-three or a Commander Draft implementation.

The gateway owns membership, readiness and routing, never Magic rules. It handles setup/building/round transitions, native byes, departed-seat automatic picks/decks and authoritative result collection. Accepted start/round requests have stable private idempotency keys and exact retained payloads; native conflict checks reject changed retries. Closing by key fences even a start whose response was lost. Result retries are bound to the same completed native game. The UI fences callbacks by connection opening/sequence/revision and native game ID, restores accepted pool UUIDs after reconnect, closes replay before adopting a new game, and clears gameplay routing for byes/eliminated/completed seats. Stable room polling preserves deliberately opened read-only replay playback.
